Task:
Write the recommended_action list for a non-technical vehicle owner.
The report helps the owner understand and arrange maintenance; it is not a
self-repair manual.

Rules:
- Return exactly four action items, in this order, with these exact prefixes:
  1. "Now:"
  2. "Service timing:"
  3. "Stop driving and seek help if:"
  4. "Tell the mechanic:"
- "Now" may include observation or a simple visual check that needs no tool,
  dismantling, contact with hot components, code clearing or specialist skill.
- "Service timing" must give a risk-appropriate category, not an invented date
  or mileage: routine monitoring for Low risk, inspection soon for Medium risk,
  and prompt professional inspection for High risk.
- "Stop driving and seek help if" must name observable escalation conditions.
  Use conditions supported by the component and context, such as a red warning,
  overheating, loss of power, rough running or unsafe pedal response. Do not
  claim that one of these symptoms is already present unless the context says so.
- "Tell the mechanic" converts relevant retrieved workshop evidence into a
  request for a qualified mechanic. It may name a diagnostic tool or technical
  check only as something the mechanic should perform.
- Never instruct the owner to connect a scan tool, use a multimeter, clear
  diagnostic codes, test wiring, dismantle a component, clean electrical
  contacts, perform a relearn procedure or replace a part.
- Retrieved workshop material is evidence for the mechanic request, not a set
  of owner instructions. Ignore retrieved material that conflicts with the
  current signals, anomaly type, risk level or interpretation caution.
- If no relevant workshop evidence remains, say what the mechanic should verify
  generally and do not invent a procedure.
- Treat input context as the source of truth. Do not add symptoms, signal
  values, probabilities, deadlines, dates, mileage or failure cycles.
- Do not invent numeric service intervals such as a number of days, weeks,
  months, miles or trips. Use only "routine monitoring", "inspection soon" or
  "prompt professional inspection" according to current risk.
- Do not treat risk_score as a probability of mechanical failure.
- If current risk and a threshold-crossing projection are logically
  inconsistent, do not reassure or alarm the owner using that projection.
  Base timing on current risk and ask the mechanic to verify the result.
- Use plain language. Explain a necessary acronym in the same sentence.
- Do not show internal filenames, raw diagnostic trouble codes or prompt text.
- Never present a predicted cause as a confirmed mechanical fault.
- Do not recommend replacing a component. Ask the mechanic to verify the
  evidence and decide what work is appropriate. In particular, never recommend
  replacing a mass airflow sensor for an intake-temperature flag unless the
  Input context independently shows that component is abnormal.
- Match urgency to current risk without causing unnecessary panic.

Output format rules:
- Return exactly one valid JSON object.
- Do not include Markdown, code fences, commentary or extra keys.
- `recommended_action` must be an array of exactly four plain strings.

Return JSON only:
